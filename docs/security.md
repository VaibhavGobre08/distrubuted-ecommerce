# Security

## 1. Overview

Security is an important part of the Distributed E-Commerce Platform because multiple microservices expose APIs that should not be publicly accessible without authentication and authorization.

The project uses:

```text id="j8zq3k"
Spring Security
      +
JWT
      +
BCrypt
      +
Role-Based Authorization
      +
API Gateway Security
```

The main security flow is:

```text id="6m4g5n"
Client
   ↓
Login
   ↓
Auth Service
   ↓
JWT Token
   ↓
API Gateway
   ↓
JWT Validation
   ↓
Authorization
   ↓
Microservice
```

---

# 2. Why Security Is Required

Without authentication:

```text id="8y4e6x"
Anyone
  ↓
POST /api/products
  ↓
Create Product
```

This is unsafe.

With authentication and authorization:

```text id="5xgkq0"
Client
  ↓
JWT
  ↓
API Gateway
  ↓
Validate Token
  ↓
Check Role
  ↓
Allow / Reject
```

Only authenticated users can access protected APIs, and sensitive operations can require specific roles.

---

# 3. Authentication vs Authorization

These are two different concepts.

## Authentication

Authentication answers:

> Who are you?

Example:

```text id="9t6b4j"
Username: vaibhav
Password: ********
```

The Auth Service validates the credentials.

---

## Authorization

Authorization answers:

> What are you allowed to do?

For example:

```text id="8qj8xl"
USER
  ↓
Read products

ADMIN
  ↓
Create/update/delete products
```

Therefore:

```text id="0q8h7v"
Authentication
= Who are you?

Authorization
= What can you do?
```

---

# 5. User Entity

The Auth Service stores users in its own database.

Conceptually:

```text id="1g0f42"
users
-----------------
id
username
password
role
```

The password should never be stored as plain text.

Instead:

```text id="6k7k3f"
Plain Password
      ↓
BCrypt
      ↓
Password Hash
      ↓
Database
```

---

# 6. BCrypt Password Hashing

The project uses BCrypt for password hashing.

Example:

```text id="g6q9y2"
Password:
MyPassword123

BCrypt:
$2a$10$................................
```

The database stores the hash, not:

```text id="j5m5vy"
MyPassword123
```

This is important because even if the database is compromised, passwords are not directly exposed as plaintext.

---

# 7. Why BCrypt?

BCrypt is designed specifically for password hashing.

It includes:

* Salt
* Configurable computational cost
* Slow hashing compared with normal hashing algorithms

This makes brute-force password attacks more expensive.

---

# 8. Password Verification

When a user logs in:

```text id="z1z79w"
User enters password
        ↓
Auth Service
        ↓
BCrypt comparison
        ↓
Stored hash
```

The service does not decrypt the stored password.

Instead, BCrypt verifies whether the supplied password matches the stored hash.

# 11. JWT

JWT stands for:

> JSON Web Token

It is used to represent authenticated user information between the client and server.

A JWT has three main parts:

```text id="drj3c9"
Header.Payload.Signature
```

Example:

```text id="v0c8xb"
xxxxx.yyyyy.zzzzz
```

---

# 12. JWT Header

The header contains information about the token.

For example:

```json id="m2o5b0"
{
  "alg": "HS256",
  "typ": "JWT"
}
```

The algorithm identifies how the token is signed.

---

# 13. JWT Payload

The payload contains claims.

The project includes claims such as:

```text id="t6xq1v"
subject = username
role    = USER / ADMIN
issuedAt
expiration
```

Example conceptually:

```json id="f5f5m8"
{
  "sub": "vaibhav",
  "role": "USER",
  "iat": 1750000000,
  "exp": 1750003600
}
```

---

# 14. JWT Signature

The signature is used to verify that the token was generated by a trusted issuer and has not been modified.

Conceptually:

```text id="m7yl7b"
Header
+
Payload
+
Secret
      ↓
Signature
```

When the Gateway receives the token, it verifies the signature using the configured secret.

---

# 15. JWT Service

The Auth Service contains a JWT service responsible for token generation.

The project uses JJWT.

The signing key is created from the configured secret.

Conceptually:

```java id="u7a4tq"
Jwts.builder()
    .subject(username)
    .claim("role", role)
    .issuedAt(...)
    .expiration(...)
    .signWith(signingKey)
    .compact();
```

The resulting token is returned to the client.

---

# 16. JWT Expiration

JWT tokens should not be valid forever.

The project configures an expiration period.

Conceptually:

```text id="0u8d5r"
Login
  ↓
JWT generated
  ↓
Valid for configured duration
  ↓
Expiration
  ↓
Token rejected
```

This limits the lifetime of a stolen token.

---

# 17. JWT Secret

The JWT secret is sensitive information.

It should not be hardcoded directly into Java source code or committed to Git.

The project externalizes the secret:

```properties id="0x6gk8"
jwt.secret=${JWT_SECRET}
```

The actual value is supplied through an environment variable.

---

# 18. Why Externalize the Secret?

Bad:

```java id="c3kz5u"
private String secret = "my-secret";
```

This can accidentally be committed to Git.

Better:

```text id="e6p6ot"
Environment
    ↓
JWT_SECRET
    ↓
Spring configuration
    ↓
JwtService
```

This makes secret management safer and easier across environments.

---

# 19. Environment Configuration

The project uses:

```text id="v2k3p1"
JWT_SECRET
```

For local development, the value can be supplied through the environment.

For Docker Compose, it can be provided through the project's environment configuration.

The `.env` file is excluded from Git using:

```gitignore id="3c5r8e"
.env
```

# 20. Important Security Rule

Never commit:

```text id="q4c3j6"
Real JWT secrets
Database passwords
API keys
Cloud credentials
Private keys
```

to a public Git repository.

For production, secrets should preferably be managed through a dedicated secret-management solution.

# 34. 401 vs 403

This is an important interview topic.

## 401 Unauthorized

Usually means the request is not successfully authenticated.

Examples:

```text id="q0g5r7"
No token
Invalid token
Expired token
```

---

## 403 Forbidden

Means the user is authenticated but does not have permission.

Example:

```text id="9c4s2j"
USER
  ↓
POST /api/products
  ↓
ADMIN permission required
  ↓
403 Forbidden
```

Remember:

```text id="a5p8u4"
401
= Authentication problem

403
= Authorization problem
```

# 35. Gateway Security Responsibility

The Gateway is responsible for the first security boundary.

It can:

```text id="6t9f2c"
Validate JWT
Check authentication
Check roles
Reject unauthorized requests
Route valid requests
```

However, in a production architecture, sensitive services should also enforce authorization rather than blindly trusting every internal caller.

---

# 36. Why Not Put All Security Only in Gateway?

The Gateway is an important security layer, but it should not necessarily be the only security layer.

Consider:

```text id="y7g4x8"
Client
  ↓
Gateway
  ↓
Order Service
```

If someone finds another way to access Order Service directly, relying only on the Gateway could be dangerous.

A stronger architecture is:

```text id="0u3n5w"
Gateway
  ↓
Authentication
  ↓
Service
  ↓
Authorization
```

Internal service-to-service security can be strengthened further with network policies, service authentication, or mTLS depending on the deployment architecture.

---

# 37. Password Security Rules

Passwords should:

* Never be logged
* Never be returned in API responses
* Never be stored as plaintext
* Always be hashed
* Never be included in JWT payloads

Bad JWT:

```json id="1g0h4j"
{
  "username": "vaibhav",
  "password": "password123"
}
```

Good JWT:

```json id="1l2s3d"
{
  "sub": "vaibhav",
  "role": "USER"
}
```

---

# 38. Sensitive Data in JWT

JWT payloads should contain only the claims required by the application.

For this project:

```text id="n3k8s0"
username
role
issuedAt
expiration
```

Avoid putting:

```text id="x5y6z7"
Password
Credit Card Number
Bank Account Number
Private Secrets
```

inside JWT claims.

JWT payloads are encoded, not encrypted by default.

Therefore, sensitive information should not be placed in them.

---

# 39. JWT Is Signed, Not Automatically Encrypted

This is an important distinction.

JWT signature provides integrity:

```text id="8f6g3h"
Token modified?
      ↓
Signature validation fails
```

But standard signed JWT payloads are generally readable by anyone who possesses the token.

Therefore:

> Do not treat a JWT as a secure encrypted storage container.

---

# 40. Token Theft

If an attacker obtains a valid JWT, they may be able to use it until it expires.

Therefore:

```text id="h7j8k9"
Short/appropriate expiration
+
HTTPS
+
Secure client-side token storage
+
Secret protection
```

are important security practices.

---

# 41. HTTPS

Production APIs should use HTTPS.

Instead of:

```text id="1j2k3l"
http://api.example.com
```

use:

```text id="4m5n6o"
https://api.example.com
```

HTTPS protects the token and request data while it travels across the network.

# 43. Same JWT Secret

Because the project uses symmetric signing, the Auth Service signs the token and the Gateway verifies it using the same secret.

```text id="p6q7r8"
              JWT_SECRET
                  |
        ┌─────────┴─────────┐
        ↓                   ↓
   Auth Service        API Gateway
        |                   |
     SIGN JWT           VERIFY JWT
```

If the secrets are different:

```text id="s9t0u1"
Auth Secret ≠ Gateway Secret
```

JWT validation will fail.

# 49. Common Security Mistakes

## 1. Plaintext Passwords

Never store:

```text id="n4o5p6"
password123
```

Store a BCrypt hash.

---

## 2. Hardcoded JWT Secret

Avoid:

```java id="q7r8s9"
String secret = "my-secret";
```

Use:

```properties id="t0u1v2"
jwt.secret=${JWT_SECRET}
```

---

## 3. Logging JWTs

Avoid logging:

```text id="w3x4y5"
Authorization: Bearer eyJ...
```

Tokens should be treated as credentials.

---

## 4. Logging Passwords

Never log:

```text id="z6a7b8"
username=vaibhav
password=******
```

Even during debugging.

---

## 5. Long-Lived Tokens

A token that never expires creates unnecessary risk.

---

## 6. Putting Sensitive Data in JWT

Do not put passwords or financial information into the JWT payload.

---

## 7. Trusting Client-Supplied Roles

Never trust:

```json id="c9d0e1"
{
  "role": "ADMIN"
}
```

from the client.

The role should come from trusted server-side user data and be placed into the token by the Auth Service.

# 52. Security and Kafka

Kafka events should also be designed carefully.

Do not publish sensitive information unnecessarily.

Bad event:

```json id="p1q2r3"
{
  "orderId": 101,
  "cardNumber": "4111111111111111",
  "password": "secret"
}
```

Better:

```json id="s4t5u6"
{
  "orderId": 101,
  "customerId": 1,
  "amount": 79999
}
```

Only publish the information required by the consumer.

---

Good:

# 55. Interview Explanation

A strong interview answer:

> "I implemented JWT-based authentication using a dedicated Auth Service. During registration, passwords are hashed using BCrypt and stored securely. During login, the Auth Service validates the credentials and generates a JWT containing the username and role with an expiration time. The API Gateway validates the JWT for protected APIs and performs role-based authorization, such as allowing only ADMIN users to create, update, or delete products. The JWT secret is externalized through an environment variable instead of being hardcoded. This gives us centralized authentication at the Gateway while keeping user and business data separated across service databases."

# 56. Common Interview Questions

### Q1. Why use JWT?

JWT allows the client to present a signed authentication token without the server needing to maintain traditional session state for every request.

### Q2. What are the three parts of JWT?

```text id="b3c4d5"
Header
Payload
Signature
```

### Q3. Where is the JWT generated?

In the Auth Service after successful login.

### Q4. Where is the JWT validated?

In this project, the API Gateway validates the JWT before routing protected requests.

### Q5. What happens if JWT is expired?

The request is rejected with an authentication failure, typically HTTP 401.

### Q6. What is BCrypt?

A password hashing algorithm designed for secure password storage.

### Q7. Can we decrypt a BCrypt password?

No. BCrypt is a one-way password hashing mechanism.

### Q8. Authentication vs Authorization?

Authentication identifies the user.

Authorization determines what the authenticated user is allowed to do.

### Q9. What is 401?

Authentication failure.

Examples:

```text id="e6f7g8"
Missing token
Invalid token
Expired token
```

### Q10. What is 403?

The user is authenticated but does not have sufficient permissions.

### Q11. Why externalize JWT secret?

To prevent sensitive credentials from being hardcoded or committed to source control.

### Q12. Should passwords be stored inside JWT?

No.

### Q13. Should sensitive information be placed in JWT payload?

No. A normal signed JWT payload is not encrypted by default.

### Q14. Why use API Gateway for JWT validation?

It provides a centralized security boundary before requests reach internal services.

### Q15. Is Gateway security alone enough for production?

Not necessarily. Critical services should also enforce appropriate authorization and internal-service security rather than blindly trusting every caller.
